# AZ-104 文件題庫（`BANK_DOC`）延伸開發規格

本文件是**只給 `BANK_DOC`（文件題庫，`AZ104/tools/bank_doc.current.js`）用**的延伸規格，記錄
Question Set 2 及之後要繼續匯入時需要的背景知識。轉錄整理自 `az104-skeleton` 分支（commit `a60555d`，
2026-07-30）的 `AZ104-SPEC.md`——那條分支獨立蓋了一整套跟 main 不同的架構（獨立的
`az104-engine.html`、`banks/` 目錄、Python 工具鏈），已確認**不會再有後續開發**，所以把裡面
「怎麼轉錄這份 PDF」的知識搬回 main、依 main 現在的檔案結構調整過，避免分支之後若被清掉，這些
踩過的坑跟盤點結果一起不見。

**跟 main 現有架構的差異，先講清楚**：`BANK_DOC` 目前只有 40 題（Question Set 1 全部），走的是
main 的共用引擎（`AZ900/az900-practice.html` 換殼、`AZ104/tools/build_practice_html.js` 組頁），
**不是**下面提到的 `az104-engine.html`／`banks/`／`tools/build.py` 那一套；領域分頁也維持 main 的
**3 個分頁桶**（見 `AZ104-SPEC.md` §5），不是 skeleton 分支自己蓋的 5 分頁版本。下面內容裡凡是
跟這兩點衝突的地方，都已經在段落裡註明「main 走法不同」。

## 2. 「AZ-104 有幾題」有三個答案，14 組重複題答案互相矛盾

**題數會有出入，這是來源文件本身的性質，不是掃描錯誤：**

| 算法 | 題數 |
|---|---|
| 三份檔案原始題數合計 | 546 |
| 只看 `NEW-AZ-104-470Q.pdf` 一份 | 470 |
| 扣掉真重複之後的唯一題數 | 約 505 |

出入來自三件事：
1. 兩份增題有 76 題，但其中 19 組其實已經在 470Q 裡；兩份增題彼此也重疊 5 組。
2. 470Q 自己內部也重複：真重複共 29 組、多出 41 題（同一題在不同 Question Set 出現好幾次）。
3. **系列題不是重複，不能砍**：22 組、共 86 題屬於「同一段共用情境、每題提出不同 `Solution:`」
   （見 §5 系列題寫法）。單純比文字相似度會誤判成重複——比對要把「情境」與「解法」分開比，
   兩段都相同才算重複。

**收錄時以 470Q 為主**：同一題已經用 `S1`–`S6` 收過了，就不要再用 `NewQ` 收一次；
只有增題獨有的那些題才會出現 `sec:"NewQ"`。

### 14 組重複題的標的答案互相矛盾（要人工裁決）

最乾淨的例子是題組 4 的 #43 與 #81：題目、四個選項、附的表格一字不差，但一處標
A（Proximity2 only）、另一處標 C（Proximity1 only），連文件自己的說明都互相打臉。

**處理原則**：遇到答案矛盾的，出圖把題目與表格看清楚、自己判斷正解，並在解析裡寫明
「原始文件在 X 與 Y 兩處給了不同答案，這裡採用 Z，理由是…」（比照 main 既有內容處理
`AZ104-Q375`/`AZ104-Q411`/`AZ104-Q401` 那幾組矛盾題的方式，見 `AZ104-SPEC.md` §11）。

## 3. 題號：`sec` + `no` 兩個欄位（已在 `bank_doc.current.js` 採用）

三份來源檔各有各的編號方式，470Q 又分 Question Set 1–6 與 Testlet 1–10、**每一段的
`Question #` 都從 1 重新算**，所以單一數字認不出是哪一題，一定要兩格：

```js
{sec:"S1",   no:1,  …}   // Question Set 1 · Question #1
{sec:"T3",   no:2,  …}   // Testlet 3 · Question #2
{sec:"NewQ", no:63, …}   // NewQ #63
```

| `sec` | 對應 | 範圍 |
|---|---|---|
| `"S1"`…`"S6"` | 470Q 的 Question Set 1–6 | `no` 各自 1 起算，最多到 121 |
| `"T1"`…`"T10"` | 470Q 的 Testlet 1–10（案例研究） | `no` 各自 1 起算，最多到 4 |
| `"NewQ"` | 兩份增題（#1–#62 與 #63–#76 是同一系列） | `no` 1–76 |

main 的 `AZ104/tools/validate.js`／`build_practice_html.js` 已經支援讀取 `sec`/`no`/`code`
（見 `AZ104-SPEC.md` §5、§10），新題目照這個格式加進 `bank_doc.current.js` 陣列即可，
`code` 欄位比照現有 40 題的寫法設成 `"S1#1"` 這種 `sec + "#" + no` 字串。

缺號只在同一段之內有意義——題組 1 到 #40 結束，題組 2 又從 #1 開始，兩者之間沒有「缺號」可言。

## 5. 轉錄 AZ-104 題目時的坑（跟 AZ-900 不同的地方）

AZ-900 是 fundamentals，題目大多是「這個服務是做什麼的」。AZ-104 是 associate，題型重心不同：

1. **情境題會長很多**——常見「某公司有 A、B、C 三個環境，需求是 X，你該怎麼做」，換行分段
   （`AZ900-SPEC.md` §10）要比 AZ-900 更吃重，前言、需求、問句要分開。
2. **PowerShell／Azure CLI／ARM／Bicep 的程式碼片段**——AZ-900 沒有這種東西，已經確認過排版
   並修好引擎（輕量 markdown，見 `AZ104-SPEC.md` §9、`AZ900-SPEC.md` §9-1b）。
3. **入口網站截圖題會更多**——選項是入口網站畫面（側欄、刀鋒、設定清單）就一定要設
   `fix:true` 不洗選項，`validate.js` 目前**還沒有**擋這件事，加題時自己注意
   （AZ900-SPEC.md §5 的 `fix` 欄規則適用）。
4. **案例研究（case study）＝ Testlet，會遇到 `[待決]`**——10 組 Testlet、共 23 題，
   每組有一段共用的 Introductory Info（公司現況、需求、既有環境），底下掛 1–4 題。
   main 的引擎**目前沒有這個題型**。兩條路：
   - 拆成獨立題：把共用情境複製進每一題的 `q`。不用動引擎，但同一段情境會重複 2–4 次。
   - 替引擎加一個 `case` 欄位：一組情境存一份，渲染時折疊顯示。比較貼近原廠，但要動引擎。

   **先問使用者，不要自己決定。** 題組 1–6 的 447 題可以先做完，不必卡在這裡。
5. **實作題（lab）**——官方沒有公布哪些考試有 lab，AZ-104 作答時間 100 分鐘
   （官方分類是「不含 lab」的那一檔），但仍可能出現。練習頁不模擬 lab。

## 6. 拖放題（`dd`）的兩種答案區

原廠的 DRAG DROP 有兩種長相，`tgt` 的寫法不同：

**一、左右配對** — 答案區每一格都有描述文字。`tgt` 就放那些描述，可以標 `⟦⟧`，不設 `fix`
（兩邊都洗）。這是 AZ-900 的主流形態。

**二、建立清單（build list）** — 答案區是沒有標籤的 N 個空格，只有上下順序。`tgt` 用
`["第 1 個","第 2 個",…]`（英文 `["Slot 1",…]`）並**設 `fix:true`**，答案區不洗、只洗可拖曳的項目。

現有的 `BANK_DOC` 兩題 `dd`（`S1#20` Key Vault＋存取原則、`S1#23` Site Recovery 三個物件）
都屬於第二種。⚠️ **順序是不是答案的一部分，要在解析裡講清楚**——這兩題原文問的都是
「要建立哪些物件」，是集合而不是順序，但引擎是逐格批改，只能照原始文件圖上的上下順序排，
解析末尾要寫明這件事。

## 7. 系列題的寫法

「同一段共用情境、每題提出不同 `Solution:`」的系列題共 22 組 86 題，題組 1 就有 6 組
（`S1#38`–`S1#40` 就是一組，已在現有 `BANK_DOC` 裡）。慣例：

- **每一題都完整收錄**，共用情境照抄進每一題的 `q`，不共用、不省略。它們是不同的題目。
- 第一段用「注意：本題與另外數題的情境完全相同，但每一題提出的解法不同，請個別判斷解法是否
  達成目標。」（渲染成 `.qnote` 小字灰底，與題目分開）。
- `解法：…` 自成一段並整段標 `⟦⟧`，對應 PDF 的排版。
- 解析裡互相引用同組的其他題，用 `` `S1#38` `` 這種來源座標。
- 整組只有一題是「是」是常態，但也可能全部都不是——那種要回頭確認。
